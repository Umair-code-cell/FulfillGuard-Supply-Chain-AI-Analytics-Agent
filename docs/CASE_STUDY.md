# Case study: investigating historical delivery performance

## Business context

Operations analysts need a reliable way to inspect late deliveries across purchase cohorts and geographic segments. Repetitive KPI queries are often simple to calculate but can be misinterpreted when models invent values, mix populations, or suggest unsupported causes. FulfillGuard explores one bounded AI-assisted workflow for answering these questions with a visible source trace.

## Dataset

The local development import of the [Olist Brazilian E-Commerce dataset](https://www.kaggle.com/datasets/olistbr/brazilian-ecommerce) recorded **99,441 orders**, **99,441 customer records**, **112,650 order-item records**, and **3,095 sellers**. Recorded purchase dates ran from **2016-09-04** to **2018-10-17**. The importer records SHA-256 file hashes and checks referential integrity, but cannot independently authenticate the downloaded files. Original data and generated databases are excluded from this repository.

## Business metric definition

The late-delivery KPI uses orders with `order_status='delivered'` and non-null actual and estimated delivery dates. It groups orders by **purchase date**, and counts an order as late when the **date portion** of actual delivery is after the estimated date. Its denominator excludes undelivered and missing-date orders. Seller-location segmentation uses order–seller pairs and must not be interpreted as distinct order counts.

## Reproducible measured example

**Question:** What proportion of delivered orders purchased in São Paulo (SP) during July 2018 arrived late?

**Tool:** `delivery_kpis(start='2018-07-01', end='2018-07-31', state='SP')`

**Observed SQL results in the imported local database:** 2,712 eligible delivered orders, 100 late orders, **3.69%** late-delivery rate, average delivery duration **6.71 days**. These numbers were computed from the stored database, not generated by the model. The values are contextual to this KPI's eligibility and purchase-date definition.

## Engineering solution

A Groq model can map a supported user request to one of five allowlisted tools. The backend executes parameterized SQL with read-only SQLite access; the agent tracks the returned values using evidence IDs and validates reported numeric claims against the tool output. A deterministic offline baseline provides a non-LLM comparator. Docker, FastAPI and a lightweight browser dashboard make the workflow reproducible locally.

## Measured validation and technical limitations

A 43-test suite passed locally, and the deterministic Olist baseline passed 22/22 selected scenarios. A separate historical 28-case live-model evaluation completed 23/28 requests without exception, with 60.7% expected-tool coverage and 67.9% evidence-reference validity. These measurements are **not accuracy claims**. The live benchmark exposed mismatched tool choices, refusals, unsupported numbers and narrative suppression; details and reproduction steps appear in [EVALUATION.md](EVALUATION.md).

## Value and responsible interpretation

The prototype demonstrates a traceable path from a supported supply-chain business question to a defined KPI and explainable SQL result. It does **not** quantify analyst time saved, establish root causes of delays, or constitute a production deployment. Those outcomes require a separately designed user study, stronger semantic evaluation and operational controls.
